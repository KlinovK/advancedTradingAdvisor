# Extended financial accounting policy contract (TG-7.5.6-A2)

Status: **product policies D1–D10 approved by the portfolio owner; architecture implementation contract, not production activation**. The six fee rules and correction projection are approved accounting behavior. All numbers in the golden cases are `Decimal` values constructed from strings. This document makes no tax, custody, or trading-execution claim. The fee-aware domain, schema v5, importer, and reconciliation remain unimplemented.

## A. Scope and existing boundary

The intended scope is one USDT-accounted portfolio spanning multiple owned account locations and imported Binance Spot executions. It includes historical holdings, cost, realized PnL, transfers, provenance, and read-only reconciliation. It excludes order placement, tax reporting, automatic balance adjustments, live exchange access, and changes to the legacy Advisor snapshot or Telegram flows.

The [v4 contract](financial-ledger-persistence.md) and current [values](../../src/advanced_trading_advisor/financial/values.py), [ledger](../../src/advanced_trading_advisor/financial/ledger.py), [replay](../../src/advanced_trading_advisor/financial/replay.py), [repository](../../src/advanced_trading_advisor/storage/postgres_financial_repository.py), and [schema](../../src/advanced_trading_advisor/storage/postgres_schema.py) implement immutable opening/buy/sell operations, exact postings, USDT settlement, weighted-average replay, and portfolio-local atomic append. They do **not** implement fees, account locations, imports, transfers, corrections, or reconciliation. `OpeningFacts.incomplete_quantity` covers unknown-cost *quantity*; it cannot faithfully encode a known principal plus an unknown additive fee on the same units. The current enum calls fully unavailable cost `UNKNOWN`; the new public completeness term below is `UNAVAILABLE`. Existing v4 rows and their meaning must be preserved.

## B. Accounting principles and arithmetic

1. USDT is the accounting currency. A fill's asset units and USDT amounts are separate facts; a non-USDT quote pair requires independently evidenced execution-time USDT conversion before it can enter a USDT ledger. Never infer a price from current market data.
2. Use the existing portfolio-wide weighted-average cost policy. Balances are tracked per account location; **only the portfolio aggregate has a cost pool**. An internal transfer changes location quantities, never portfolio quantity, known cost, or unknown-cost components. Do not report location cost basis or location PnL in the first version. An exchange fill is one immutable financial event per actual execution, not one event per order.
3. Persist gross execution facts, actual fee asset/quantity, source identity, exact signed asset postings, and valuation evidence. Never replace gross facts with net numbers alone. `Decimal` input and output retain the v4 finite, 60-digit, 24-place limits; proportional allocations use the v4 120-digit half-even context and 24-place quantum, with final disposal taking the residual. No implicit rounding of input facts.
4. Reject any effective historical prefix with negative asset or USDT quantity at a location and at portfolio aggregate for new location-resolved events. Existing v4 aggregate-only rows retain their aggregate validation and remain unassigned to a location until an explicit, evidenced allocation policy exists. A future deposit cannot cure an earlier deficit. Conservation means every balance change has an identified fill, flow, fee, or correction cause; it does not mean that unlike asset quantities add to zero.
5. Recorded facts remain append-only. A correction changes the *effective projection* through linked reversal/replacement facts while retaining the original and every audit event. Recompute all later weighted-average allocations. Use the same portfolio row lock, full-history validation, atomic transaction, and portfolio-local sequence as v4.
6. Never show a cost or PnL total as complete when any required cost or valuation component is missing. An observed exchange balance is evidence for reconciliation, not permission to create a ledger posting.

Notation: `Q` is gross base traded; `P` is gross quote principal in USDT; `f` is fee quantity in its own asset; `F` is the independently evidenced execution-time USDT value of a third-asset fee; `C(x)` is historical weighted-average cost removed for `x` units; `→` lists signed balance postings. All six approved fee rules assume a USDT-quoted pair and exact, separately recorded fee facts. Non-USDT pairs are excluded from the first automated importer and quarantined under D3. Fee amounts must be nonnegative; a zero fee is an explicit zero fact and creates no zero posting. A rebate is a distinct, deferred event, never a negative fee smuggled into these rules.

## C. Approved trading-fee policies (D1, D2, D6)

| Fill and fee | Gross/net quantities and exact asset postings | Approved cost and PnL treatment | Evidence and failure behavior |
| --- | --- | --- | --- |
| BUY, base fee | Gross base `Q`; received base `Q-f`; `base +(Q-f), USDT -P`. Persist gross `+Q` and fee `-f` as separate causal legs even if the location balance projection nets them. | Capitalize the base fee into the acquired net units: basis `P` on `Q-f`. No separate fee disposal PnL. | Require `0 <= f < Q`, positive net, gross fill and commission evidence, and enough USDT for `P`. No independent fee valuation. Reject zero/negative net or insufficient USDT. |
| BUY, quote fee | Gross/net base `Q`; total quote outflow `P+f`; `base +Q, USDT -P, USDT -f`. | Acquired basis `P+f`; no separate PnL. | Require enough USDT for both legs and exact quote-fee evidence. Sum with the 120-digit context and reject a value outside domain limits. |
| BUY, third-asset fee | Base `+Q`, USDT `-P`, fee asset `-f`. | Basis `P+F` for acquired base; fee-asset disposal removes historical basis `C(f)` and has realized PnL `F-C(f)`. These are distinct numbers; **never** use `F` as historical fee-asset basis. | Require fee-asset balance, `F` with timestamp/source/conversion method, and historical fee-asset cost to report both PnLs complete. If `F` is missing, base basis and component PnL are incomplete even though `P` is known. If `C(f)` is unknown, fee-asset PnL is unavailable. Reject insufficient fee asset/USDT; do not invent `F`. |
| SELL, base fee | Gross sale `Q`, additional base fee `f`, total base outflow `Q+f`; `base -Q, base -f, USDT +P`. | Remove `C(Q+f)`; sale PnL `P-C(Q+f)`. No separate fee-asset sale line. | Require held base >= `Q+f`, gross sale/commission evidence. No independent fee valuation is needed for this aggregate PnL. |
| SELL, quote fee | Gross base outflow `Q`; gross quote `P`, net received `P-f`; `base -Q, USDT +P, USDT -f`. | Remove `C(Q)`; sale PnL `(P-f)-C(Q)`. | Require `0 <= f <= P`, exact commission evidence, and nonnegative net quote. An evidenced zero-net execution is permitted with gross proceeds and fee separately recorded; v4 positive-proceeds facts remain unchanged. |
| SELL, third-asset fee | `base -Q, USDT +P, fee asset -f`. | Sale component `P-F-C(Q)`; fee-asset disposal component `F-C(f)`; combined realized PnL `P-C(Q)-C(f)`. The `F` terms cancel only in the combined total. | Require fee-asset balance and historical costs. `F` is required to report *component* PnLs; when absent, combined PnL may still be complete if both historical costs and `P` are complete. Reject insufficient base or fee asset. |

For any disposal with partially or fully unknown historical cost, retain exact quantities and known cost components but do not calculate a complete PnL. A third-asset fee with unknown acquisition history does not become a zero-cost fee. If the fee asset equals the traded base or quote, use that same-asset row, not the third-asset row. Posting roles must distinguish principal, gross acquisition/disposal, and fee even when two postings share an asset. Acquisition fees are capitalized under D1; expense-only BUY treatment is not the approved policy. A fee's quantity can affect basis and PnL only once.

## D. Cash flows and location boundary

Every location has an opaque stable identity and an ownership/coverage record. Do not infer ownership from an exchange address or label. A deposit/withdrawal observation records external source/destination evidence where known, amount, network fee, timestamp, and coverage; it is not automatically a trade.

| Event | Exact postings and aggregate effect | Approved cost and PnL policy |
| --- | --- | --- |
| Opening balance | `location/asset +q`; aggregate `+q`. | Existing v4 known, partial, or unknown opening semantics remain valid at portfolio aggregate. A new location-specific opening needs separate evidence; do not silently assign v4 balances to an exchange account. No PnL. |
| Deposit from outside tracked portfolio | `destination/asset +q`; aggregate `+q`. | If purchase provenance supports a cost, attach it; otherwise acquisition cost is unavailable. No realized PnL from receipt alone. An inbound transfer from another owned location is *internal* only when both sides are tracked and linked. |
| Withdrawal to outside tracked portfolio | `source/asset -q`; aggregate `-q`. | Move proportional known/unknown basis out of tracked scope. A move to the same owner's untracked wallet has no trade PnL only when portfolio-owner registration and transfer evidence establish ownership; preserve exported basis/provenance for later re-entry. A gift, spend, sale, or unverified ownership is quarantined for review, not inferred as a transfer. |
| Network fee | Additional `source/fee_asset -f`; aggregate `-f`, separately from delivered `q`. | Remove historical basis `C(f)` from the portfolio cost pool. Independently evidenced execution-time value `F_network` is the fee expense; separately report fee-asset disposal PnL `F_network-C(f)`. Never label `C(f)` as execution-value expense. If either value is unknown, its dependent component is incomplete. Fee in a different asset requires its own balance and cost check. |
| Internal transfer | `source/asset -q`, `destination/asset +q`; aggregate zero. A separately charged fee is another causal leg. | Portfolio-wide cost and unknown-cost components remain exactly unchanged; no PnL. There is no location cost allocation to move. Atomic pair with stable transfer identity; never create the destination credit without the source debit. Reject insufficient source balance. |
| External transfer with unverified ownership | Record observed inbound/outbound evidence, but do not automatically pair it or assign cost. | Quarantine for review. Matching by amount and time alone is insufficient; neither PnL nor basis continuity is asserted. |

Withdrawal API quantities can be quoted before or after network fee; the adapter must explicitly map the provider's observed debited, delivered, and fee quantities and verify `debited = delivered + fee` where those fields are present. Do not assume that relation if the provider's evidence is incomplete. Account locations must be explicitly registered by the portfolio owner; a matching address, amount, or timestamp alone is not proof of same ownership. Unclassified spending/gifts remain outside automated posting until reviewed. A future performance metric may choose a presentation, but cannot change these ledger facts.

For a sale or external withdrawal, first verify sufficient units at its source location; then remove cost from the **portfolio-wide** pool using the portfolio-wide weighted average. No per-location cost or PnL is computed. For example, if A holds 1 BTC and B holds 1 BTC while portfolio cost is 300 USDT, moving 0.4 BTC from A to B leaves portfolio quantity 2 BTC and cost 300 USDT. A later sale from A removes portfolio-average cost of 150 USDT per BTC, regardless of which location supplied the unit. Location-level basis would require a separate approved allocation model; no such value is inferred here.

**Approved network-fee example (D5).** Fee `0.01 BTC`, historical basis removed `0.8 USDT`, independently evidenced execution-time value `1.2 USDT`. Expense is `1.2`; fee-asset disposal PnL is `1.2-0.8=0.4`; combined impact is `-0.8`. These are separate quantities, not two fee deductions. Missing `1.2` evidence makes expense and disposal PnL unavailable; missing `0.8` basis makes disposal PnL unavailable even if expense value is known. No current price or tax characterization is implied.

**Historical Binance USDT valuation (D2, D5).** Accept an immutable historical Binance record that directly states the fee's USDT value, or one unambiguous historical Binance Spot fee-asset/USDT execution price at the **same valuation instant** as the accounting event. For a price record, compute `F = fee_quantity × price` with `Decimal`; its quote asset must be USDT. Retain provider, dataset/endpoint or archival extract identity, record/trade ID, symbol, price or direct USDT amount, original timestamp and resolution, normalized UTC valuation timestamp, fill execution timestamp, fee quantity, and calculation method. The source record must be independently retrievable or archived and tied to the exact event; an order's own non-USDT fee amount is not itself a USDT valuation. Match timestamps at the source's stated resolution with no invented time tolerance. Reject a stale record, differing timestamp, ambiguous same-instant prices, missing USDT pair, unsupported source, or unrepresentable product; do not round to fit the 24-place domain limit. Missing evidence leaves affected acquisition basis or component PnL `PARTIAL`/`UNAVAILABLE` as section H specifies. The B3/S3 fixture's `E1` is an explicit assumed qualifying record, not a claim that Binance supplies one for every execution. No live price substitution or invented conversion is allowed.

## E. Exchange fill identity and deterministic import

Canonical source identity is `(portfolio_id, provider, exchange_account_key, symbol, event_namespace, external_execution_id)`. Namespace `spot_trade` uses the ordinary Spot `trade_id`. Namespace `sor_allocation` uses `allocation_id` and can never collide with a trade ID. **SOR import is unsupported in the first version:** persist/quarantine detected allocations for review, without balance postings or a silent drop. Never treat `allocationId` as `tradeId`. Store provider `binance_spot` as a versioned enum, a non-secret opaque account key, canonical symbol, and the provider's exact identifier string. Store and compare `order_id`, side, UTC execution timestamp, gross base `quantity`, gross quote `quote_quantity`, `commission`, and `commission_asset` as immutable payload evidence. Order ID is **not** the fill key: partial fills and multiple fills from one order each have separate execution identities. Preserve source precision and an immutable normalized hash for conflict detection, but never use a hash alone as proof of economic equivalence.

One immutable **source-identity record** owns that canonical key; immutable event versions reference its ID. An identical key and identical active canonical facts returns the active operation and its original sequence/recorded time without writes. A changed source payload is quarantined as a conflict until an authorized correction creates a linked new version; it is never silently overwritten or added as a second active fill. A client operation UUID remains portfolio-scoped idempotency for manual input; the natural key independently prevents duplicate imports with different UUIDs. A missing or untrustworthy execution ID cannot be automatically imported using order ID, timestamp, or a content hash as a substitute. Require manual review and a stable explicit source identity. Store import batch/coverage evidence separately.

Sort an import batch by UTC execution time and authoritative provider execution order when available; never use API response/page order. Persist a portfolio sequence and retain v4 `(executed_at, sequence)` order for v4 facts. For equal-time new events with no authoritative order, evaluate all economically distinct orderings against the full prefix, including **already committed** events at that timestamp; if the comparison is infeasible, quarantine rather than guess. If cost, PnL, or validity differs, quarantine the candidate and any still-uncommitted ambiguous peers before append until an explicitly recorded manual order is approved; do not mutate existing committed facts. A lexical ID sort is not economic evidence. If every ordering gives the same state and outputs, choose a stable canonical key order and record that tie rule. Example: initial 1 BTC with cost 100 USDT and 200 USDT cash; same-time buy 1 BTC for 100 USDT and sell 1 BTC for 200 USDT. Buy-first leaves 1 BTC with cost 100 and sale PnL 100; sell-first also leaves 1 BTC with cost 100 and sale PnL 100, so it is immaterial. In contrast, initial 1 BTC cost 100 and 200 USDT cash, same-time buy 1 BTC for 200 and sell 1 BTC for 300: buy-first removes cost 150 and PnL is 150, while sell-first removes cost 100 and PnL is 200; both leave 1 BTC but with different cost. Quarantine that pair if not yet committed; if one event was already committed, quarantine the late peer pending an authoritative or manual order and replay review. Backdated imports replay every later prefix under the portfolio lock and either commit the entire candidate or reject without a sequence gap. A partially imported account is not marked complete merely because all retrieved pages were processed; explicit coverage windows and source pagination evidence are needed.

**Immutable effective ordering key (D7, D8).** Every committed economic slot has `(executed_at_utc, effective_order_path)`; `recorded_at` and monotonic portfolio `append_sequence` remain separate audit fields. A path is a nonempty finite tuple of signed integers compared lexicographically, with a shorter proper prefix sorting before its children. V4 rows retain a *virtual* path `(sequence)` so their pairwise replay order remains exactly `(executed_at, sequence)` without rewriting v4 data. New v5 rows store an immutable unique effective path at their timestamp; under the portfolio row lock, choose an unused path strictly between the approved predecessor and successor. Integer-tuple paths have space between any two finite paths by extending a prefix; the domain and PostgreSQL comparator must agree exactly. If storage cannot represent a required path, quarantine rather than renumber existing paths. Correction replacements inherit the original economic slot path in the **effective projection**; audit versions keep their own append sequences and cannot create a second active slot. Replay sorts effective rows by `(executed_at_utc, effective_order_path)` and rejects duplicate active paths, invalid chronology, or any invalid historical prefix. The key alone is not ordering evidence: record provider execution order when available or a portfolio-owner resolution ID, reason, compared source records, and chosen predecessor/successor. All ordering evidence and path assignment are immutable and committed with the event. No API response order, lexical ID, or late arrival is treated as authoritative.

Ordering examples are separate histories. **A:** v4 operations at the same time with sequences 2 and 5 have virtual paths `(2)` and `(5)`; their order is unchanged. **B:** two same-time v5 fills, with evidenced first→second order, append sequences 10 and 11, can receive paths `(2,1)` and `(2,2)` between existing v4 paths `(2)` and `(3)`. **C:** an existing v5 fill at time `t` has append sequence 20/path `(2,2)`; a late fill recorded later with append sequence 21 can receive path `(2,1)` when evidence places it before the existing fill. Replay then processes 21 before 20 at `t` without changing append history or either existing path. **D:** the section J same-time BUY/SELL pair yields PnL 150 or 200 depending on order; absent authoritative or owner-approved resolution, both remain in a separate quarantine record with no effective path, posting, or append sequence. A late peer to a committed fill is likewise quarantined until resolved and full replayed. When no v4 neighbor exists, choose paths using the same between-neighbors rule. No fabricated provider order is assumed.

## F. Approved append-only correction projection (D7)

Corrections are audit events with their own IDs, sequences, recorded times, portfolio-owner actor identity, mandatory nonempty reason, target version ID, source/valuation evidence references, and immutable linkage. Only the authenticated owner of that financial portfolio may authorize a correction in this first version; the domain/repository accepts an already verified owner identity from the future application boundary and records it, without introducing multi-user RBAC. The source-identity record and its unique exchange key remain unchanged. A replacement version references that same source identity and includes complete new facts/provenance; it does **not** claim the unique source key a second time. The target version remains stored and queryable. Each source identity has at most one active version at any committed point; a pure reversal leaves none. Further changes target the active version, forming an acyclic chain. An identical correction ID, target version, and replacement content is idempotent; conflicting reuse fails. Two concurrent corrections to one active version serialize under the portfolio lock and one conflicts. An authorized correction may resolve a quarantined changed source payload; a routine importer cannot do so.

The effective replay projection treats a linked reversal and replacement as **one atomic group at the target's historical slot**, then recomputes every later weighted-average allocation. Inverse postings are retained as audit legs but are **excluded from ordinary effective balance sums**; all balance/PnL reads must use the version-aware effective projection, never raw summation over audit rows. A pure reversal leaves no active economic version; a replacement substitutes one new active version. Check each *effective* historical prefix, all location balances, cost completeness, and sequence/linkage integrity before commit. `recorded_at` is captured at authorization/append and may be later than `executed_at`; the inherited effective path preserves historical order and cannot silently reorder equal-time independent fills. A backdated standalone operation uses its actual execution slot and the same full replay gate. Commit owner authorization evidence, reason, source-version linkage, audit legs, active-version resolution, postings, and `last_sequence` in one transaction under the portfolio row lock; an error rolls back all of them.

If the corrected acquisition has already funded a disposal, a changed basis revises the derived PnL of that later disposal without altering the disposal's immutable facts. Every report must identify an immutable ledger/report revision (at least committed `last_sequence` plus calculation-policy version), its as-of time, and the coverage snapshot; a later correction produces a new report revision and does not rewrite a prior report. Unresolvable provider conflicts, changes across ownership boundaries, an ambiguous same-time order, an impossible historical balance, or an unsupported cost allocation require manual review. There is no retroactive database UPDATE/DELETE, automatic repair, or tax restatement policy here.

## G. Read-only reconciliation contract

Input: portfolio, account location, asset, observed free quantity, observed locked quantity, UTC observation time, source and observation ID, and coverage status/window. Ledger projection must be computed at the same observation cutoff. Compare observed `free+locked` with ledger account total. Compare free and locked separately only if the ledger actually models reservation state; otherwise mark bucket comparison **UNAVAILABLE**, never assume all ledger units are free. Report exact Decimal delta `observed - ledger` with no tolerance-based auto-rounding.

Classify: `MATCH`, `QUANTITY_MISMATCH`, `MISSING_LEDGER_ASSET`, `MISSING_OBSERVATION`, `STALE_OBSERVATION`, `INCOMPLETE_COVERAGE`, `LOCATION_UNMAPPED`, or `UNAVAILABLE`. These labels are diagnostic, not postings. A mismatch can prompt review of missing fills, deposits, withdrawals, fees, clock skew, or account mapping, but no cause is assigned without evidence. Store observation and coverage metadata append-only or in a separately auditable read model; never auto-post a balancing adjustment. A complete aggregate comparison requires complete coverage of every included location and consistent observation cutoffs.

## H. Financial completeness contract

| Status | Cost or PnL meaning | Reconciliation meaning |
| --- | --- | --- |
| `COMPLETE` | Every required historical cost and fee valuation is evidenced and representable; exact total may be shown. | Every relevant location/asset observation and ledger cutoff is covered and comparable. A complete comparison can still report a mismatch. |
| `PARTIAL` | Exact known component/subtotal exists, but an unknown component prevents a complete total. Expose the known component and missing-reason set; never label it the total. | Some locations/assets/windows are comparable; show covered comparisons and the coverage gap. |
| `UNAVAILABLE` | Required evidence is absent or no meaningful known subtotal exists. Do not return zero as a substitute. | No trustworthy comparable observation or ledger projection exists. |

Cost evidence must distinguish unknown **quantity basis** from unknown **additive cost on known quantity** (such as an unvalued third-asset BUY fee). A complete acquisition cost requires both. An unknown component propagates through weighted-average allocations and later disposals; a disposal touching it has incomplete realized PnL. Portfolio calculation is `COMPLETE` only when every included disposal is complete; `PARTIAL` may expose a labeled subtotal of complete components but no total; `UNAVAILABLE` means even that subtotal is not meaningful. For a third-asset SELL fee without `F`, component PnLs are unavailable, but the combined PnL can remain calculable if `P`, `C(Q)`, and `C(f)` are complete. Arithmetic overflow or an unrepresentable allocation is a validation failure, not a rounded `COMPLETE` result.

**Separate source-history coverage (D9):** `COMPLETE` requires an owner-evidenced opening accounting boundary for every registered source account/location and asset, opening quantities, explicit known or unknown opening cost, an inventory of supported event types, uninterrupted source time windows and pagination/cursor evidence through the report cutoff, no missing supported event IDs, no unresolved quarantined or unsupported events (including SOR), and a timestamped total-balance reconciliation at the boundary and cutoff with no unexplained quantity mismatch. Retain account identity, source extract identifiers, window endpoints, page/cursor or sequence evidence, observation IDs/timestamps, compared balances, discrepancies and their reviewed resolution. Successful API pagination alone is never proof of full history. `INCOMPLETE` means a known gap, unsupported event, unresolved quarantine, or unexplained reconciliation mismatch; `UNKNOWN` means the opening boundary, source account identity, or continuity cannot be established. Reconciliation status remains a separate diagnostic dimension, while an unresolved mismatch blocks `COMPLETE` coverage. A documented, evidenced scope exclusion may be recorded, but cannot make a portfolio-wide total complete if affected assets remain in scope.

Publication rule: show unqualified portfolio cost/PnL `COMPLETE` **only if calculation and source-history coverage are both `COMPLETE`**. Otherwise show calculation as a ledger-only provisional result with its own status and mark the published result `PARTIAL` only for a clearly isolated subtotal whose own asset/location history and all cost inputs have complete coverage; if gaps may affect that subtotal, mark it `UNAVAILABLE`. Never publish a complete portfolio total. A recorded opening of 1 BTC at cost 100 and sale of 1 BTC for 150 yields ledger-only PnL 50; a known missing earlier acquisition gives coverage `INCOMPLETE`, so published portfolio PnL is `UNAVAILABLE` as a total, never 50 as proven. Unknown coverage has the same publication restriction. Calculation can be `COMPLETE` while coverage is `INCOMPLETE` and reconciliation reports `QUANTITY_MISMATCH`; these statuses must not be collapsed. Unknown acquisition cost never becomes zero cost. The existing v4 `UNKNOWN` enum retains its v4 meaning; new public `UNAVAILABLE` is a separate versioned reporting contract.

## I. Additive schema v5 implementation contract

Preserve all v4 rows, IDs, sequences, postings, and existing fee-free meaning. Extend the existing financial operation/posting tables and strict mapper with versioned, type-specific fields and constraints; do not silently reinterpret v4 fields as net fee-inclusive values. v5 requires a migration that adds columns/tables and deliberately replaces the v4 operation-type/posting-role CHECK rules and deferred posting validator with **stronger rules for each new type while preserving the v4 branches**. Calling the migration "additive" describes data compatibility, not an assertion that DDL can avoid constraint/function replacement.

| Required v5 data | Minimum persisted contract |
| --- | --- |
| Extended event facts | Type/version discriminator; gross base/quote quantity, quote asset, side, fee asset/quantity, optional evidenced fee value in USDT, valuation method/source/time; exact principal and causal posting roles. Preserve v4 fact columns as-is. |
| Effective ordering | Immutable effective path for v5 economic slots, unique among active events at one `(portfolio_id, executed_at)`; v4 derives virtual `(sequence)` without row rewrites. Store evidence/resolution references separately from append sequence and `recorded_at`. PostgreSQL and domain lexicographic comparators must agree. Quarantined events have no active path or financial posting. |
| Locations and flows | Portfolio-scoped opaque location ID, ownership/coverage state; posting location nullable only for legacy v4 rows; source/destination location and external boundary for transfer/deposit/withdrawal; transfer linkage and delivered/network-fee quantities. New events require location identity. No invented backfill of v4 account location. |
| External identity | A unique source-identity row keyed by `(portfolio_id, provider, account_key, symbol, namespace, external_execution_id)`; immutable version rows reference it. Store order ID, side, execution timestamp, gross quote, commission and asset in each version. Enforce at most one effective version per source identity and compare all facts on retry. Unsupported SOR allocations remain quarantined. |
| Correction links | Target ID, successor/correction group ID, reversal/replacement kind, effective slot, reason/actor audit, uniqueness of active successor, acyclic chain validation. Original immutable rows remain. |
| Evidence and coverage | Append-only valuation evidence references and import coverage windows, source page/cursor metadata without credentials; reconciliation observation table/read model with observed free/locked and cutoff, not financial postings. |
| Completeness | Separate unknown-quantity and unknown-additive-cost components, evidence/reason references, and derived `COMPLETE/PARTIAL/UNAVAILABLE` status. Do not store a fabricated zero for missing value. |

All new numerical fields use unconstrained PostgreSQL `NUMERIC` with v4-compatible finite, magnitude, scale, and sign checks; Python still validates Decimal representation. Add portfolio-scoped foreign keys and uniqueness, precise type-specific nullability/shape checks, deferred exact posting-set checks, and immutable operation/posting protections for new types. The unique exchange key belongs to the source-identity record, not each correction version. Effective-version resolution must be unique and transactional; raw audit postings cannot be treated as effective balances. The importer and expanded repository share the existing portfolio row lock and `last_sequence`; no second sequence allocator or ledger authority.

**Version-aware readiness and mapping are mandatory.** Today's `POSTGRES_SCHEMA_VERSION=4`; `validate_legacy_schema` accepts `(3, POSTGRES_SCHEMA_VERSION)`, so raising the constant alone would reject complete v4 legacy databases. V5 code must explicitly accept complete v3, v4, and v5 for ordinary legacy Advisor runtime, reject partial/corrupt versions, and require a fully validated v5 shape for new financial event writes. Existing v4 financial reads on a complete v4 database remain supported by a v4 mapper. `financial_mapper._fields` requires exact columns while repository history loads use `SELECT *`; adding v5 columns therefore requires version-dispatched projections with explicit column lists and v4/v5 row mappers, not passing v5 rows to the v4 mapper unchanged. Validate each schema version's exact tables/columns, constraints, posting triggers, immutable triggers, and function definitions; preserve the v4 operation/posting rule branches during the v5 migration. The explicit `initialize`/`advisor setup` path must remain the only migration entrypoint; ordinary readiness and append must not auto-upgrade. Test empty initialization, populated v4→v5 migration preserving every row/result, complete v3/v4 legacy readiness, v4 financial reads, v5 financial write readiness, and rejection of partial migrations and altered guards. V4 financial code cannot safely read v5 events, so deploy v5-capable code and explicit migration in a coordinated, backed-up rollout with a restricted runtime role. Downgrade must not drop or rewrite immutable history; application rollback is only safe before any v5 fact is written, otherwise use a deliberate forward fix. No migration is created by this document.

## J. Approved golden accounting cases (not executable tests yet)

Each case uses one portfolio, location **A**, an evidenced opening at `t0`, a fill at `t1`, and `source-history coverage=COMPLETE` for all relevant assets/events through `t1`.
